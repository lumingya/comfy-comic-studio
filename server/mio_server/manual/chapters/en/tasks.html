CHAPTER 05 / THE MIO HANDBOOK

Jobs & uncertain results

The top bar and workshop open the same Generation tasks page for starting, pausing, retrying and selecting images. Execution records are available from task details. Created tasks freeze their parameters and workflow documents; changing recent preferences does not alter them. Generation fills scenes with no adopted image. Reruns create candidates without silently overwriting your selection.

If ComfyUI accepts a job but history or image download is interrupted, its result stays uncertain. With a known prompt ID, reconciliation retrieves it without resubmitting. A lost submission response without an ID still needs manual verification. Cancellation discards results that have not entered the save stage; if saving has already begun, that save finishes before cancellation returns.

Pause affects scheduling, not necessarily a request already accepted upstream. Cancellation is not a refund. For uncertain results, check provider records before resolving or explicitly resubmitting: repeated paid calls can create duplicate charges. Inspect job details for actual failures.

Compare closely and adopt explicitly

Open a candidate image on the board, then choose Compare (C). This pins it while you browse other candidates from the same scene. Split compare is the default: drag the divider or use Split position to reveal differences. Synchronized zoom supports 1–4×; drag the enlarged image to pan both together. Switch to Side by side and Original size for another view.

Left / Right browse candidates, 1 / 2 select the pinned or browsing side, A adopts and X rejects. Each side also has its own Adopt button. Focused divider controls keep arrow keys for adjustment. Comparing does not change adoption by itself. Escape closes the image and returns to the board.

Check received results after restart

Results already recorded in the local delivery ledger are checked against their original jobs at startup and can be applied to the work without calling the model again. A saved receipt makes repeated recovery idempotent: it does not add another candidate or reverse adoption changes made manually before recovery. Missing reliable records, incomplete output or an uncertain upstream submission still require reconciliation, not repeated retries.

External programs can inspect GET /api/v2/jobs/{id}/deliveries, then explicitly call POST /api/v2/jobs/{id}/items/{idx}/replay-result to apply an already received result. This is a local write, not generation. It is rejected while the original worker is running, endpoint state remains unrestored or the job is canceled. Canceling later work does not roll back images already saved to the episode.

Before publishing result images, the server records their owning job and stage. On restart it can verify complete local files and restore their metadata without requiring the cloud provider to offer history. Partial files and intermediate stages retain their data and staging records. The job identifies the stage and available or missing assets; it does not automatically continue later generation stages or treat incomplete images as candidates.

External orchestration and deliverables

Open API clients can call POST /api/v2/workshop/tasks with a storyboard, presets, a workflow or profile, variables, LoRA overrides, image count and dimensions in one request. auto_start starts the job after the assembly snapshot is frozen, while adopt_first adopts the first candidate. Reusing an idempotency_key returns the original task; changing its parameters is rejected explicitly.

When an episode is ready, use GET /api/v2/episodes/{id}/deliverables to inspect available outputs, then POST /api/v2/episodes/{id}/deliverables/export for offline HTML, PDF, image ZIP or long PNG output with a selected template. Exports may be asynchronous; poll the returned status and download handle. Provider credentials never appear in the deliverable response.
