> 基线：`main @ 79ea9c0`。v1 建议稿见提交 `7759fd7`。v2 记录了已拍板的决策，并加入「上限保障清单」与「技术验证闸门」。v2.1 补充三项内容：扩展系统的新机制（§2.4）、4060 8 GB 的实测数据与「爱丽丝」工作流分析（§6.6）、8 GB 显存下的方案。v2.2 记录「不下载新模型」的决定和 Portal 验证通道。

> 审查时的轻量验证：`node js/build.js dev` 通过；`node js/tests.js` 91/91；`python -m unittest` 672 项 OK（跳过 4 项）。

## 0. 结论

- 工程纪律很强：付费请求安全语义做得很细，沙盒里的轻量门禁全绿。
- 但**投入明显偏向「平台化」**：API 操作数从 40 增至 210，另有扩展 SDK v3、样式工坊、更新中心等。
- 真正决定作品效果的创作核心仍停留在「文本变量替换 + 基础文生图」，包括角色一致性、结构化剧本、排版嵌字、出图质检。
- GitHub 上的完整 CI 门禁从未通过，见 §4.2。

方向已确定：**条漫 + 本地 ComfyUI + React**。做法分三步：

1. 冻结平台功能，止血。
2. 先用约 1 周的**技术验证（Spike）**证明新架构的上限高于旧版，再决定是否全面重写。
3. 分阶段重建，每次改动都用「效果基准」衡量。

**重构的底线**：功能面可以暂时变窄，**上限不能降低**。§2 的清单是硬性规格。

## 2. 上限保障：重构不降级的承诺

### 2.1 三条硬原则

1. **ComfyUI 不做减法**
   - 以下能力全部保留：导入任意 API 格式工作流；任意字段或变量写入任意节点输入（JSON Pointer 路径）；每格覆盖节点参数；原始工作流 JSON 可直接编辑。
   - 内置模板只是默认值。Mio 只负责编排，不做模型能力的中间商：新模型、新节点、新技术一律以工作流的形式接入，不需要改 Mio 代码。
2. **所有自动化都要能手动接管**
   - 剧本规划、提示词编译、参考图挂载、自动挑图、自动排版、自动气泡，每一层都可以手动接管或锁定。
   - 每格都有「原始提示词模式」，完全跳过编译器。
   - 编译结果可见、可改；`{变量}` 系统保留为高级层。
3. **删除旧代码前必须过闸门**
   - 新版要通过下表中所有标为「保留」和「提升」的项目，并且在效果基准上超过旧版，才能删除旧代码。
   - 旧版打标签，随时可以回退。

### 2.3 暂缓的部分

这些部分只是**推迟**，上限并不降低：

- 样式工坊、主题包（含 `theme.js`）、用户脚本、可执行变量（Node 沙箱）。暂停，只保留亮色和暗色主题，将来以扩展形式回归。
- 更新中心、市场。到发布阶段再做，届时更新包需要签名校验。
- 旧画册数据不迁移。

### 2.4 扩展系统：换机制、晚开放，上限不降

我们要改的是扩展**接入核心的方式**和**开放的时间**，扩展**能做到什么**不打折。

**为什么现有机制必须换**

1. **1353 个内部函数被迫成了公开 API**。扩展 SDK v3 的 `patch(name, wrapper)` 是按函数名去包装全局函数的。只要改一个函数名或拆一个函数，扩展就会坏，核心因此被锁死。早期项目最需要的恰恰是能随时重构。
2. **它是内部脆弱的同一个根源**。`handleAction` 被 16 个模块、`render` 被 12 处包装，用的就是这种包装链。每多一个扩展就多一层，执行顺序不可控，扩展之间还会互相冲突。
3. **重写之后这些 patch 目标全部不存在**。React 里没有全局的 `render` 或 `handleAction` 可以包。现在保留这套机制，将来什么也留不下，只会持续产生维护成本。
4. **安全**。扩展、主题脚本、用户脚本、Python 插件都能执行任意代码。自己本地用问题不大；通过市场分发，就必须有明确的信任确认。
5. **目前没有第三方扩展用户**，维护成本却在实打实地支付。

**新机制怎么保证上限不降**

- **内置功能也注册成扩展**。每个面板、管线步骤、导出器、出图渠道、版式、提示词编译器，都通过同一套注册表挂进核心，做法类似 VS Code 的内置扩展。这样扩展的上限就等于核心的上限，内置功能能做的事，扩展都能做。
- **按条漫管线设计的扩展点**：
  - 出图与 LLM 渠道
  - ComfyUI 工作流模板与绑定预设
  - 管线步骤，例如上色、翻译、修脸、质检
  - 导出器与平台切片预设
  - 版式、分格样式、气泡样式、字体
  - 剧本模板（LLM 提示词）
  - 界面面板：React 组件挂在指定插槽
  - 命令、快捷键、设置页
  - 后端路由与后台任务
  - 事件订阅
- **留一个逃生口**：提供 `ctx.internal`，直接访问内部 store、服务和组件。它明确标注为不稳定、跨版本可能失效，但确实什么都能改。「能 patch 一切」的能力保留下来，只是从默认行为变成显式选择。
- **图像能力的扩展靠 ComfyUI 工作流**。新模型、新节点、新技巧直接做成工作流接入，Mio 一行代码都不用改。这是天花板最高的一层。

**时间安排**

| 阶段 | 做什么 |
|---|---|
| P1 | 建立注册表，只供内部功能使用 |
| P2–P4 | 内部功能全部通过注册表实现，同时打磨接口 |
| P5 | 接口稳定后对第三方开放，发布 SDK 文档，配套签名与信任确认 |

这叫**晚开放**，不是降上限。

### 2.5 为什么「不改」上限也会被锁住

- **数据模型**：一幕一图的模型无法表达「这一格里有谁」「这个气泡属于谁」「同一格的多张候选」。条漫的核心要素都要求改模型。
- **规模**：单分镜 512 幕上限，加上整份状态放在浏览器里，撑不起连载（几十话、数千格）。
- **代码结构**：1353 个全局函数，`handleAction` 被 16 个模块包装，扩展又按函数名 patch。每加一个功能，成本都比上一个高，任何重构都会破坏扩展。
- **安全网**：CI 从未变绿，没有可靠的保护，在旧架构上大改风险反而更高。

结论：在旧架构上叠加条漫能力，几乎要改动所有模块，成本不低于重写，结果还更脆弱。

## 3. 对开发意图的理解

- **产品**：Mio · 绘页（原 ComfyComic Studio），本地优先的「从一个故事到一本作品」工作室。
- **旧版主链路**：
  1. 分镜：逐幕提示词和台词
  2. 预设：变量、参考图、LoRA
  3. 装配：生成不可变快照
  4. 生产队列：付费安全、可恢复
  5. 画册：阅读、气泡编辑
  6. 导出
- **目标用户**：用本地 ComfyUI 的二次元创作者。新方向改为以**条漫连载**为主。
- **开发方式**：多个 AI 代理并行，靠验收测试和开发日志对抗上下文丢失。

## 5. 「效果」的度量（条漫版）

| 层面 | 指标 | 初始目标 |
|---|---|---|
| 画面 | 角色一致性通过率：按设定集外观清单做 VLM 检查 | 大于等于 85% |
| 画面 | 镜头符合率：景别、出场人物、动作是否与剧本一致 | 大于等于 80% |
| 叙事 | 一话 40–60 格能顺畅阅读：节奏留白合理、台词可读、气泡不挡脸 | 人工评审通过 |
| 效率 | 从一句话创意到可读的一话初稿 | 不超过 30 分钟（机器出图时间另计） |
| 效率 | 修一格的时间；每张被采用图的平均出图次数 | 不超过 1 分钟；可统计 |

**效果基准（`bench/`）**：

- 黄金故事一篇：2 个角色、3 个场景、12–16 格。覆盖近景、远景、背影、双人互动、情绪变化、夜景。
- 每次改管线都跑一遍，输出联系表和 `metrics.json`。
- 图片不入库，只提交指标摘要。

> 沙盒本身连不到你本机。真实出图、LLM 和本地测试经 **Portal**（本机 MCP 端点）在你的机器上运行，直连 `127.0.0.1:8188` 与本机反代。Portal 关闭时，沙盒只跑模拟和单测。
> 基准命令形如 `python -m bench …`，输出 `metrics.json`；图片不入库。

## 6. 目标架构

### 6.1 领域模型 v3（条漫版，代码与界面同名）

```text
Series 作品（连载）
├─ Bible 设定集
│  ├─ Character 角色：外观清单（发色/瞳色/发型/服装件/饰品）、自然语言描述、标签描述、
│  │                 参考图集（正/侧/背/表情）、服装变体、LoRA（按模型族）
│  ├─ Location 场景 / Prop 道具：描述 + 参考图
│  └─ Style 画风：风格描述（按方言）、风格参考图、LoRA
├─ Episode 话
│  ├─ Panel 格（按阅读顺序）
│  │   ├─ 内容：镜头（景别/角度）、出场角色 [角色, 服装, 表情, 动作, 画面位置]、场景、时间/光线、画面描述
│  │   ├─ 台词：[说话人, 文本, 类型: 对白/心声/旁白/拟声]
│  │   ├─ 条漫属性：宽度模式（全宽/内嵌/出血/无框）、画幅比例、与上一格的间距（节奏）、转场背景（纯色/渐变）
│  │   └─ 覆盖项：原始提示词模式、追加提示词、负向、种子、节点参数覆盖
│  ├─ Take 候选：出图结果 + 完整参数快照 + 评分 + 是否采用 + 修图历史
│  └─ Strip 条漫画布：每格的位置与裁切 + 嵌字层（气泡/旁白框/拟声/特效字，可跨格）
└─ Output 输出：网页与手机条漫阅读、平台切片导出、长图、PDF；画册模板（次要）

RenderProfile 出图配置：ComfyUI 实例或实例池 + 工作流组合（生成/修图/外扩/放大）+ 绑定 + 提示词方言 + 能力
Job / Attempt：统一任务引擎（继承旧版的安全语义）
```

平台切片预设需可配置。常见规格示例：LINE Webtoon 宽 800 px、按 1280 px 切片；Tapas 推荐宽 940 px。以各平台当前规则为准。

### 6.2 后端

- **框架**：Python 3.11+、FastAPI、Pydantic、uvicorn。OpenAPI 自动生成，前端 TS 类型从它生成；WebSocket 转发 ComfyUI 进度。
- **存储**：一个 SQLite 库存元数据。素材按 sha256 存到 `data/assets/`。`.mio.zip` 只作交换格式。
- **统一任务引擎**：合并两套任务系统。保留幂等键、不可变快照、租约、uncertain 状态、并发窗口、立即停止。调度支持多个 ComfyUI 实例，并按模型分组。
- **模块划分**：
  - `pipeline/`：`script`、`prompt`、`refs`、`qa`、`layout`、`lettering`
  - `comfy/`：绑定层、运行器、WebSocket、诊断、实例池
  - `providers/`：云端，非重点

### 6.4 ComfyUI 集成（一等公民）

- **绑定优先级**：
  1. 节点标题显式标签：`[mio:prompt]`、`[mio:negative]`、`[mio:seed]`、`[mio:width]`、`[mio:height]`、`[mio:ref:1]`、`[mio:mask]`、`[mio:init]`、`[mio:output]` 等。API 格式导出自带 `_meta.title`，不需要装插件。
  2. 用户手动映射，沿用旧版的 JSON Pointer 能力。
  3. 启发式识别兜底。
- **绑定规则**（来自对你日常工作流「爱丽丝」的分析，见 §6.6）：
  - **字段选择**：写成 `[mio:prompt=positive]` 可以指定写入节点的哪个字段。像 `WeiLinPromptUI.positive` 这种自定义节点字段也能写。不指定时，写入第一个非连线的字符串字段。
  - **一对多写入**：同一个标签可以出现在多个节点上，同一个值会写进所有目标。例如种子要同时写进两个 `KSamplerAdvanced` 的 `noise_seed`。
  - **绕过只在前端生效的节点**：`easy globalSeed` 这类节点靠 ComfyUI 前端的 JS 生效，通过 API 提交时不起作用。种子由 Mio 直接写进各个采样器。
  - **多个导出变体**：分组静音在导出时就已固定。同一个工作流可以导出「草稿版」（只跑底图）和「成品版」（放大加细化）两份，分别挂到草稿档和成品档。
- **工作流的角色**：生成（文生图、参考图生图）、修图（局部重绘、指令编辑）、外扩、放大精修。一个 RenderProfile 可以组合多个工作流，形成管线。
- **实时与诊断**：
  - 连接 `/ws?clientId=…` 获取进度、执行节点和预览帧。
  - 用 `/object_info` 找出缺失的自定义节点。
  - 对照模型列表找出缺失的模型文件。
- **精选模板**，按显存分档：

  | 显存档 | 生成（标签方言） | 本地参考图 / 指令编辑 | 备注 |
  |---|---|---|---|
  | **8 GB（你的 4060 Laptop）** | Illustrious / NoobAI SDXL + 角色 LoRA（已有） | **FLUX.2 Klein 4B distilled**：Apache 2.0，4 步，支持多参考编辑，官方标约 8 GB | Klein 4B 用 Qwen3-4B 文本编码器，你已有的 `qwen_3_4b` 可能可以复用，需实测；还要下载 flux2 VAE 和 Klein 4B 权重（fp8 或 GGUF） |
  | 12–16 GB | 同上 | FLUX.2 Klein 4B；Qwen-Image-Edit-2511 GGUF | Klein 9B 是非商用许可 |
  | 16 GB 以上 | 同上 | Qwen-Image-Edit-2511 FP8（约 16 GB）多参考 | — |

  另有放大与精修模板。
- **8 GB 显存下的一致性方案**（Spike 里用效果基准比较后定默认值；不下载新模型）：
  - (a) SDXL + 角色 LoRA：画风最好、速度快。原创角色需要先训练 LoRA，ComfyUI 已有原生 `TrainLoraNode`，后续可以做成「设定集 → 训练角色 LoRA」。
  - ~~(b) FLUX.2 Klein 4B 多参考~~：因为「不下载新模型」而不采用；以后换了显卡或改变决定时再议。
  - (c) 混合：GPT Image 2（经你的反代）按参考图定构图和角色，再用本地 Illustrious 低重绘幅度图生图加 NoobAI tile ControlNet（已有）统一画风。简称「云端定形，本地定画风」。
- **草稿档 / 成品档**：先用草稿档（只跑底图）给每格出 K 张候选；选定后只对采用的图跑成品档（迭代放大、部位细化）。8 GB 显存必须这样分，吞吐才够用。

### 6.5 核心管线

```text
一句话创意 / 小说片段
  → LLM 结构化剧本（JSON Schema；不支持时退回 json_object，再校验和修复）
  → 话 / 格（镜头、出场角色、表情、台词、条漫节奏）         ← 可编辑，可锁定
  → 设定集（外观清单 + 参考图集；可一键生成三视图 / 表情表）  ← 挑选锁定
  → 提示词编译（标签方言 / 自然语言方言）+ 按出场角色挂载参考图 ← 可切到原始模式
  → ComfyUI 出图：每格 K 个候选，实时预览
  → VLM 质检（外观清单 + 剧本符合度）→ 自动挑选 / 标红 → 单格修图（局部重绘、指令编辑、外扩）
  → 条漫画布：按格属性自动排版（间距、宽度模式、转场）       ← 可拖拽微调
  → 自动嵌字：人物 / 人脸框 → 气泡避让、阅读顺序、尾巴指向说话人、竖排、拟声
  → 导出：平台切片、长图、PDF、网页阅读、.mio.zip
```

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 重写陷入低谷期或半途而废 | Spike 闸门、旧版标签可回退、以垂直切片推进 |
| 新版上限反而更低 | §2 的三条原则加能力对照表作为验收；ComfyUI 不做减法 |
| 本地显存门槛高（8 GB） | 草稿档 / 成品档分离；8 GB 档默认用 FLUX.2 Klein 4B 和 SDXL LoRA；混合方案可选；支持任意工作流，由用户自带 |
| ComfyUI / Portal 经公网隧道暴露 | 没有鉴权时，任何人都能提交任务、查看出图历史（`/history`、`/view`）、上传文件，还可能通过 ComfyUI-Manager 安装节点，相当于远程执行代码。**只在联调时开隧道，用完即关**；长期使用请加 Cloudflare Access 或带令牌的反向代理，并调高 Manager 的安全等级。有了 Portal 之后，ComfyUI 不再需要公网隧道。Portal 端点等于远程 Shell，令牌等同密码：不用时停止 Portal，并定期更换令牌 |
| 扩展系统被误认为降级 | 采用 §2.4 的注册表机制：内置功能也注册成扩展，并保留 `ctx.internal` 逃生口 |
| VLM 质检不稳定 | 结构化清单、多次投票，最终由人拍板 |
| 沙盒无法真实出图 | 沙盒里只跑模拟和单测；真实基准在本地跑，回传 `metrics.json` |
