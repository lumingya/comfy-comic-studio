## M1：画布路径排除条件依赖后，静默把有歧义的多阶段采样控制自动绑定到后阶段

**位置**：`server/mio_server/comfy/binding_scope.py:23-30,96-107,125-141`，以及 `server/mio_server/comfy/binding_inference.py:337-339,378-397`。

**独立源码因果**：原图的后阶段 `/33` 经 `/8` 解码到 `/9` 输出。其初始画布来自 `/34` 的端口 1；前阶段 `/3` 的初始画布来自同一节点的端口 0。更关键的是，`/3` 的结果经 `/36` 的 `stage_c` 依赖进入 `/33` 的 `positive`。因此 `/3` 也是最终输出的实际执行祖先，并非未消费或被旁路的独立支线。两个阶段都有上述三个独立字面量控制。

`binding_scope.py:27-29` 把 `positive`、`negative`、`conditioning` 统一列为非画布端口。`_role_inputs(..., canvas=True)` 因此在 `/33` 停止沿 `positive` 追踪；这一依赖又不会触发“不完整／未知”的回退，因为它已在非画布集合里。按当前规则手工推导的画布节点集合为 `{9,8,33,34}`，只含采样点 `/33`。`primary_sites()` 返回 `/33` 后，`binding_inference.py:378` 给它开放 steps、cfg、sampler 等自动控制，并把 `/3` 排除在这三项之外。源码没有在自动决定前检查：被排除的条件祖先中是否仍有另一个尚未判明角色的采样阶段。

这解释了当前三次请求只改 `/33` 且无警告的实测。`compile.py:326-345` 只在对应 kind 没有绑定时发出值被忽略的警告；这里已有错误地确定下来的绑定，故不会进入手动接管提示。

**为何构成通用阶段语义缺陷**：区分主画布和参考／控制分支是合理目标，但“经条件端口进入后续采样器”本身不能证明上游采样器只是参考、也不能证明用户的通用采样参数应只作用于后阶段。这个真实样本正好展示了必要的前阶段生成结果通过条件边进入下一阶段。当前泛化规则把“不是直接画布传递”转成了“可以自动选择后阶段”，超出了图结构本身能够证明的语义。无需否定现有真正参考分支的保护，也无需退回沿所有依赖一概选择前阶段；应在阶段角色无可信契约时保留歧义并交给用户选择。

**历史与本轮分开判定**：历史自动改 `/3` 也不满足原先 manual 预期，不能据此把前阶段写成真值。本轮从 `/3` 改为 `/33` 另有固定请求行为变化，但这一点不是本发现成立的前提；独立的失败标准是：两个合法候选仍存在时，无配置地自动写其中一个，并且没有提示选择。不能通过重写 oracle 为“后阶段正确”消除失败。

**影响及分级**：用户明确提交的采样控制会静默作用于未经确认的阶段，改变实际生成行为；这是导入推断的核心能力和通用多阶段适用性问题，故为 Medium 并阻止本职能最终 PASS。本证据没有显示源文档／连接／其他字面量被破坏，且现有逐请求测量称连接保持相同，故不据此上升为 High 或宣称不可逆数据损坏。

**修复要求与验收边界**：用通用的阶段歧义判定或可信的语义契约处理这种“采样结果经条件边进入另一个采样阶段”的情况；不能只加 sample1 节点类名补丁，也不能把所有条件依赖都当主画布。角色不明时，上述三个 kind 应保持无自动写入并明确提示手动 mapping；用户显式选择任一阶段后应只改所选目标。已有证据记录两个阶段的六次独立手动操作均精确命中，因此手动落点本身可行。需要增加保留这种歧义的中性回归，并继续保留真正生成参考分支、直接 latent／重编码图像的串联阶段、输出端口隔离等现有契约。当前 `test_workflow_canvas_scope.py:86-109` 只覆盖直接画布传递；`test_workflow_semantic_bindings.py:305-361` 将中性条件支线预设为 reference，不能证明真实的阶段条件链都可采用同一自动归属。

### 公开调用和类型边界核对

探针不是直接篡改内部 plan。`probe.py:83-92,229-241` 先调用正式 `slot_adapters.describe(doc)` 取得活跃组与条目的真实稳定键，再向正式 `compile_workflow(doc, {}, slot_overrides=...)` 提交数字 `strength=1`。两种结构分别是平铺编号字段和单个 Power 形态字典槽位，原模型权重为有限数字字符串 `"0.375"` 和 `"-0.375"`，原 CLIP 权重为 `"-0.25"` 和 `"0.25"`。图通过普通 `WorkflowDoc` 构造，未注入私有冻结计划，也没有提供伪造发现结果。

该路径确为产品公开路径：`api/library.py:188-192` 的 LoRA 发现端点调用同一 `SA.describe`；`:248-260` 的编译预览端点把请求的 `slot_overrides` 交给同一 `C.compile_workflow`。这里只核实入口映射，没有声称本次进行 HTTP 实测。`render_models.py:39-66` 的图类型与 API 图验证不会把这些字段的字符串强制转成数字；`workflow_slot_shapes.py:74-124` 也会识别这两种槽位，并不会因权重为字符串而声明只读。因此问题不在于探针绕过了一个实际会拒绝此数据的公共类型门禁。

### 独立根因核对

1. `workflow_slot_common.py:108-109` 的 `_is_number` 只承认原生 `int/float`。`workflow_slot_values.py:51-58,66-72` 用它读取两种堆栈，于是把有限数字字符串模型权重替换成语义默认值 `1`，同时遗漏字符串 CLIP 权重。`slot_adapters.py:170-189` 将这些 plan 中的 pinned 值直接作为发现值返回。
2. 请求经 `workflow_slot_overrides.py:28-38,94-115` 正常规范化，明确数字 `1` 成为浮点 `1.0`，仍有合法稳定键；`workflow_slot_selection.py:37-51` 确实把它合并进选中条目。因此不存在请求未进入解析器或键不匹配的问题。
3. `workflow_slot_apply.py:120-127` 比较合并结果与 pinned。当误读的默认值是整数 `1` 时，Python 的 `1.0 == 1` 使整个条目判为相同，直接跳过写入，而且只设 `wrote=True`，没有提示该明确请求未改动原字段。`compile.py:310-316` 因此接收到原图副本和空 notices。
4. 即使只修发现读取，写入侧仍有第二处相同的语义偏差：`workflow_slot_writers.py:157-182` 的 `_stack_value` 也把数字字符串当模型 `1`、无 CLIP；后续 `:194,222-226,242-256` 依赖这个快照判断哪些字段要改。两侧需要共享一致的数值解析，不能只修发现显示或移除最外层 no-op 判断。

这是同一深层契约的重复实现发生分歧：链式读取 `workflow_slot_values.py:19-36`、对象列表读取 `:91-103` 已通过 `_num` 解析数字字符串；两种堆栈却维持另一套原生类型判定。`workflow_slot_syntax.py:61-68` 已有拒绝布尔、非有限值且不额外进行两位小数舍入的解析边界，可作为统一语义的参考。保留未改字段的原生字符串表示，与正确解析其数值用于比较并不冲突。

### 实测事实、分级与验收

封存的 C07/C08 结果分别记录：发现模型 `1`、CLIP `null`；稳定键明确请求 `1` 后，编译图仍为原模型字符串 `"0.375"`／`"-0.375"`；警告均为 0，源文档均不变。已静态检查探针的顺序：它先完成正式编译，读取编译图中的实际字段，核对源文档未变，再保存 observed，最后才执行默认值断言。因此虽然首个断言在发现值处失败，结果里的“请求后仍未改”不是凭该断言推测出来的，而是在断言之前已取得的实际编译输出。

我独立确认该项 **Medium** 成立：一个被正常识别为可编辑的既有条目，在请求被接受后静默丢失明确权重修改，直接违反稳定键精确覆写与无损编辑目标。它影响通用结构与数值表示，不能靠插件类名补丁修复。没有证据显示源文档损坏或节点已在外部实际执行，故不拔高为 High。两个案例共享一项根因，不另列两个缺陷；也不声称这是此次范围新引入的回归。

修复后至少需要独立验证：这两种结构的发现值反映真实数值；稳定键明确从非 1 改为 1 确实写回；单独改 CLIP 或模型只改变指定字段；未改权重、名称、包装元数据及原生类型精确保留；不可解析／非有限值明确拒绝或给出可行接管提示，而不是静默替换为可编辑默认值。现有本项测量已足以阻止最终 PASS，无需在本审查再增加产品调用。
