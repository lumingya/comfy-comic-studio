## 当前流程

1. 五位审查者分别检查规范、需求、持久化、隔离桥与前端、扩展生态与 SDK；各自只写自己的报告。
2. 主控把发现集中到[发现与修复台账](FINDINGS.md)，确认触发条件后分配修复文件。修复者保留回归证据，主控精准提交与推送。
3. 新的审查者读取台账与相关报告，检查实际修复并尝试反证。未通过时继续修复；原作者不承担自己的独立复审。
4. 本轮改动复审关闭后，再派新的审查者检查原改动列表之外的项目文件，并重复修复、独立复审与验证。
5. 最后核对全部发现状态、生成一致性、相关门禁和最终提交的远端 CI，形成最终摘要。

## 证据要求

- 每个缺陷给出文件/位置、触发输入或竞态、预期/实际、影响及最短离线复现；合理怀疑单列，不能当作已复现。
- 区分规范与需求两条审查轴。工具已覆盖的格式项不重复报告；架构异味是判断依据，不自动等于缺陷。
- 查看原报告前先形成自己的攻击路径；既有测试和上一轮审计结论可用于定位，不能代替当前证据。
- 所有实验使用临时工作区、中性素材和模拟服务。随包数据保持保护，截图/大文件/密钥不入库，真实付费调用不在本轮范围。
- 子代理读共享台账并仅编辑约定文件；生成物、共享台账、提交和推送由主控统一协调。
