# Mio 2.2.3 — 直接重命名与连续失败保护

2026-09-14 · [教程中心](README.md) · [安全升级](guide/CONTENT_AND_SHARING.md)

## 画册菜单改为「重命名」

原来的「批量编辑名称 / 标签」只有标题前缀输入，不能修改现有名称。本版改为「重命名」：

- 选一本时，输入框直接显示这本画册的完整现有名称。
- 多选时，每本画册都有自己的名称输入框，可以分别修改；不是统一追加前缀，也不强制改成相同名称。
- 名称须为 1–150 字。先验证全部输入，任何一本无效都不部分提交。
- 取消不改动；保存只修改选中的画册名称，不改变图片、原标签、画册 ID、原图目录、源计划或生成快照。
- 按需读取所选画册的完整文件后再改名，避免只修改懒加载摘要而丢失正文。
- 若画册被删除、名称被其他操作修改、或开始生成/重绘，拒绝按过时的对话框覆盖。
- 409/500 或响应丢失时明确显示「重命名尚未确认」，保留本页待保存名称；普通保存重试不会重复追加名称。

### 标签为什么保留

现有标签参与画册搜索，可以在画册集搜索框输入标签查找作品，不是完全无用的数据。因此保留已有标签和搜索用途，**从重命名窗口移除追加标签输入**，不擅自批量删除用户已有标签。重命名只负责名称。

## 连续失败暂停上限

位置：**创作画册 → 生成队列 → 失败策略 → 连续失败暂停上限**。

- 默认 **5**，可配置 **0–100**；**0 表示关闭这项保护**，不是无限自动重试。每幕自动重试上限仍然生效。
- 每份画册生成任务单独计数，跨分镜累积；首次尝试与自动重试发生的失败都计入，成功一次清零。生成前校验失败也算失败尝试；只读结果核对不增加计数。
- 按服务端实际记录结果的顺序计算连续性，而不是按分镜编号。并发情况下也不会丢计数。
- 达到上限时，暂停当前任务的后续自动请求，同时撤销它已有的重试倒计时；**不是只跳到下一幕再开始新一轮重试**。
- 其他画册仍可继续，已经完成的图片和原始错误记录保留。
- 已发出的并发请求可完成并保存结果，所以最终失败记录可能超过上限；停止后不会再自动派发新的生成请求。已经领取但尚未发出的分镜会停在发送前，不虚增请求次数。
- 迟到的成功可以清零连续计数，但**不会解除已经触发的暂停**。刷新、重启、恢复全局调度或调高/关闭上限也不会悄悄恢复该任务。
- 检查服务后，使用现有的「继续未完成分镜」并确认，从原任务继续；重置连续计数和暂停标记，保留已完成幕，不另建一册或重画已完成图片。
- 调低上限时，如果当前累计次数已经达到新值，会立即暂停，不必再等一次失败。

### 与原失败策略的关系

该上限独立于每幕重试次数，也适用于「不自动重试、其他分镜继续」模式。401/403/429 等 4xx 仍不自动重试；422 保留错误并跳过，但达到连续失败上限时也会暂停。请求结果不明仍不自动重发，手动继续仍需确认可能重复计费的风险。

原来更严格的暂停条件继续有效。例如渠道配置错误会立即暂停，不必凑够连续失败次数。删除仍只需一次确认，不需要先核对供应商或放弃跟踪。

## 升级与交付

完整源码运行包，包含 59 个经过哈希核验的独立内容文件及 `data/distribution.json`；运行需要 Python 3.10+，不需要 Node.js。

停止旧服务，把新程序解压到新目录，通过 `MIO_DATA_DIR` 指向原工作区。**不要用随包初始 `data/` 覆盖个人工作区，也不要删除原 `data/runtime/execution/jobs.sqlite3`。** 新版会为原任务数据库补充计数与暂停标记字段，保留原任务、失败策略和作品；已有策略缺少新字段时使用默认值 5，不回溯重试历史请求。

本版保留 2.2.2 的独立预设草稿、另存为、预设删除及图片归属保护。验收见 [2.2.3 记录](acceptance-2.2.3/README.md)。测试使用 Linux/Chromium、临时工作区及受控本地 HTTP 服务，不声称验证付费模型或实体手机/桌面平台实机。
